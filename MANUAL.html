devtrim

Developer-machine disk hygiene for macOS: measure, classify, trim — with preview-first safety rails.

v0.1.0 · Apache-2.0 macOS 13+ Trash-first deletion Protected-path denylist --json for agents

01Philosophy

devtrim exists because cleaning a 900 GB Mac by hand is how good data dies. Every design decision enforces three rules:

  • Measure before cutting. scan is read-only and always free to run. Sizes are real (st_blocks-aware), so sparse files don't lie to you.
  • Classify by risk. Every finding carries a danger score from 1–10 that decides how hard you must confirm (see §06).
  • Trim with a net. Filesystem deletions go to macOS Trash by default — recoverable from Finder. Permanent deletion is an explicit --shred.

The tool refuses to be clever about your data:

  • Docker volumes are never pruned — a volume can hold a live production database.
  • Xcode Archives are listed but exempt — they are release artifacts.
  • Repos with recent commits are skipped, not swept.

02Install & build

git clone https://github.com/mneves75/devtrim
cd devtrim
cargo build --release        # → target/release/devtrim (~1 MB)
cargo test                   # unit tests: date math, scanners, parsers

No runtime dependencies beyond macOS itself. The binary is self-contained; put it on your PATH:

cp target/release/devtrim /usr/local/bin/     # or ~/.local/bin
devtrim --version
Rust ≥ 1.85 (edition 2024) is required to build. Runtime target is macOS 13+.

03Quick start

The 30-second tour. Everything starts as a dry-run preview:

devtrim scan                        # full report across every category
devtrim clean caches                # preview only — nothing happens yet
devtrim clean caches --apply -y     # actually move caches to Trash
devtrim icloud                      # check big files queued for iCloud upload

Reading the output:

   37.5 GB  danger:7  DerivedData  /Users/you/Library/Developer/Xcode/DerivedData
           └─ rebuilt on next build
  • size — real bytes on disk (sparse-file aware).
  • danger:N — confirmation weight; colors go green → amber → orange → red.
  • path — exactly what would be affected.
  • └─ note — why removal is safe and how it comes back.

04Command reference

Global flags work anywhere: --apply -y/--yes --yolo --shred --json --root <dir>. Click a card for details.

devtrim scan read-only

Reports every reclaimable category under configured roots plus known Library paths: package caches, stale node_modules, simulators, Xcode support files, Docker reclaimables, old Swift toolchains, agent scratch dirs.

Exit codes
0report produced (even when empty)
1a category scanner failed (others still reported)
devtrim clean caches danger ≤ 3–5

Moves regenerable caches to Trash: HuggingFace models, Codex runtimes, uv, node core cache, npm download cache, Homebrew downloads. Everything re-downloads automatically on next use.

Bandwidth note: deleting a 43 GB HuggingFace cache means re-downloading it when needed. devtrim tells you this in the note column instead of deciding for you.

devtrim clean node-modules danger 5+

Finds every node_modules under your roots, maps each to its owning git repo (nearest ancestor with .git), then classifies:

  • active — last commit within active_days (default 30): skipped, counted in stderr.
  • stale — older, or no git repo at all: proposed for removal.
  • Nested stores (.pnpm virtual store inner copies) are deduplicated — only outer roots count.

Restore any project afterwards with pnpm install or npm install; the finding notes which lockfile governs each repo.

devtrim clean simulators danger 4–6

Two-stage behavior:

  • Always: xcrun simctl delete unavailable — removes devices whose runtime was deleted. Genuinely safe.
  • Only with --yolo: additionally xcrun simctl erase all — wipes installed apps and contents of every remaining simulator. Devices survive; their state doesn't.
erase-all destroys simulator app data (test photos, logins, databases). It requires --yolo precisely because -y is too easy to type.
devtrim clean xcode danger 4+

Clears children of iOS DeviceSupport (symbol caches, rebuilt on next device debug) and DerivedData (rebuilt on next build). Parent directories are preserved so Xcode rediscovers them.

Xcode/Archives is always listed but never touched — those are App Store release artifacts. danger 0, action none.
devtrim clean docker danger 6+

Reads docker system df, proposes pruning unused images and build cache, then executes docker image prune -a -f and docker builder prune -a -f on apply.

Volumes are never pruned. A named volume may hold your live Postgres database (26 GB in one observed case). If you want volume space back, that's a deliberate manual operation after dumping data.

OrbStack users: the VM disk compacts lazily. Restart OrbStack after pruning to trigger TRIM and see host-side space return.

devtrim clean toolchains danger 6

Lists swift.org toolchains in ~/Library/Developer/Toolchains. Anything not resolved by swift-latest.xctoolchain is proposed for removal. Xcode's built-in toolchain lives inside Xcode.app and is unaffected.

Reinstall any removed chain from swift.org/install if a project pinned to it resurfaces.

devtrim clean leftovers danger 5+

Hunts AI-agent scratch that outlives its missions:

  • depth-1 dirs matching <agent-prefix>.<6 alphanumerics> (e.g. kimi-plan005-validation-resume.3rjuOR)
  • .supergoal/evidence and .supergoal/perf trees — past mission artifacts

The pattern is intentionally conservative: prefix must match known agent naming, suffix must be exactly 6 alphanumeric chars.

devtrim icloud read-only

For files ≥ 100 MB in iCloud Drive Documents, reports how much is still materialized locally (via block-count, catching sparse placeholders):

"BERLIN_E-mails.zip — 100% still local"
  └─ upload in progress; keep Mac awake and online"

Eviction (brctl evict) only succeeds after iCloud marks the file uploaded — forcing earlier risks data loss. This command lets you wait knowingly.

devtrim trash-empty danger 9

Purges everything in ~/.Trash. Requires typed acknowledgment matching current size:

devtrim trash-empty --confirm=14   # fails unless Trash holds ~14 GB (±2)

This is the one command where --apply/-y are irrelevant — the typed value is the gate. Only --yolo skips it, and you should never alias that.

05Safety model

Five independent layers stand between a typo and a tragedy:

LayerRuleBypass
Preview defaultwithout --apply, nothing mutates — evernone needed (it's the default)
Trash-firstfilesystem deletes go to ~/.Trash--shred
Danger gatescore-scaled prompts (see §06)-y ≤5 · --yolo all
Protected pathshard denylist belownothing bypasses this
Non-TTY guardpiped runs refuse mutation without explicit -y/--yoloexplicit flag

Protected paths

System roots (/System, /usr, /etc, /Applications, …) and user-critical dirs (~/.ssh, ~/.gnupg) are refused unconditionally. Under ~/Library only these managed subpaths are eligible:

Developer/Toolchains · Developer/Xcode/{iOS DeviceSupport,DerivedData}
Developer/CoreSimulator/Devices · Caches/Homebrew

The denylist cannot be disabled by any flag. If you find yourself wanting to, the correct tool is a different tool.

Size escalation

Danger scores are dynamic — big targets escalate regardless of category:

Total sizeMinimum dangerEffect
> 1 GB≥ 5-y required in non-TTY
> 10 GB≥ 7interactive y/N prompt
> 50 GB≥ 8near-Critical handling

07Configuration

Optional file at ~/.config/devtrim.toml:

roots = ["~/dev", "~/sandbox"]   # scan roots (default: ~/dev)
active_days = 30                 # commit recency defining "active" repos

CLI --root flags override config roots entirely. Unknown keys are ignored — forward-compatible by design.

08Agent integration (JSON)

Every reporting command accepts --json, emitting a stable schema suitable for coding agents:

[
  {
    "label": "DerivedData",
    "path": "/Users/you/Library/Developer/Xcode/DerivedData",
    "size_bytes": 40265318400,
    "note": "rebuilt on next build",
    "danger": 7,
    "action": "trash"
  }
]

Agent contract:

  • agents must pass -y explicitly to mutate in non-TTY mode — silent approval is refused
  • action: "trash" items are filesystem ops; "command: …" items shell out verbatim
  • action: "info" / "none" items must never trigger mutation logic
Pair well with an AGENTS.md rule: “run devtrim scan --json before proposing disk changes; propose devtrim clean … commands rather than raw rm.”

09Recipes

The quarterly deep-clean

devtrim scan                       # eyeball the landscape
devtrim clean caches --apply -y
devtrim clean node-modules         # review which repos go stale…
devtrim clean node-modules --apply -y
devtrim clean xcode --apply -y
devtrim clean simulators --apply   # check the unavailable count first
devtrim clean docker --apply       # then restart OrbStack/Docker Desktop
df -h /System/Volumes/Data

Waiting out a large iCloud upload

watch -n 300 'devtrim icloud'      # poll every 5 min
# when a file reads "~100% uploaded":
brctl evict "$HOME/Library/Mobile Documents/com~apple~CloudDocs/Documents/<file>"

Pre-flight before a big clone or model download

devtrim scan --json | jq '[.[].size_bytes] | add'   # total reclaimable bytes
devtrim clean caches --apply -y                     # make room first

Auditing what an agent did

# Trash is your audit log:
ls -la ~/.Trash | head
# restore anything from Finder (⌘Z works too)

10Troubleshooting

df says less space than expected after a clean

Three usual suspects, in order:

  • Purgeable space accounting — macOS counts some evictable content oddly between calls; trust trends over single readings.
  • OrbStack/Docker sparse disk — space freed inside the VM isn't returned until TRIM compaction; restart the VM.
  • Files went to Trash — Trash-first means space returns only when Trash empties. That's the safety net working.
non-interactive run: re-run with -y…

You piped stdin (CI, agent, script) without an explicit consent flag. That refusal is intentional — add -y for routine ops, reserve --yolo for genuinely unattended maintenance windows.

refusing protected path

A scan root or computed target intersects the denylist. Check roots in config; remember --root ~ makes almost everything protected-by-design.

Simulator storage didn't shrink after erase

erase all only runs under --yolo; plain apply does delete unavailable only. Also give CoreSimulator a minute — device bundles compact asynchronously.

Homebrew/npm cache rows show command: failures in notes

The binary wasn't on PATH in the invoking environment. Run from an interactive shell, or let the trash path handle it (brew cache dirs trash cleanly too).
